## 1. 独立判断

WorkBuddy 的主要软件故障方向有源码支持：应用初始化在内核调度启动之前调用了会睡眠的函数，伪任务 osMain 因而进入正常任务调度路径。v3 对这条已知路径的拦截位置合理。

但是，“唯一卡点是重编烧录”“所有调用都会提前报错”“时序零影响”“新固件一定完全没写入”“本机一定能出包”等结论超出了已验证范围。当前应区分三件事：

1. 烧录通信失败：最新日志在 loaderboot 传输阶段超时，没有成功完成证据。
2. 板端应用崩溃：仍出现 init/osMain/mtval=0 的故障，尚不能用这次失败的烧录验证 v3。
3. Flash 识别告警：0x80001341 有独立含义，不能与空地址访问或串口超时直接画等号。

以下路径均相对 `D:/ws/fbb/src`。

2. `middleware/utils/app_init/app_init.c:11-17`：直接依次调用注册函数；不是自动为每个回调创建线程。
3. `middleware/utils/app_init/app_init.h:49`：`app_run` 注册到上述初始化段。
4. `application/ws63/ws63_liteos_application/project/clearchain_device_app.c:256-279`：`device_app_entry` 被 `app_run` 注册；TCA9555 探测后，在第266行直接调用 `clearchain_feedback_init()`。
5. `project/clearchain_feedback.c:10-23`：初始化内执行三次 LED 闪烁。
6. `project/clearchain_led.c:53-63`：闪烁调用 `osal_msleep(on_ms)` / `osal_msleep(off_ms)`。
7. `kernel/osal/src/liteos/osal_task.c:197-200`：`osal_msleep()` 调用 `LOS_Msleep()`，然后固定返回0。
8. `kernel/liteos/liteos_v208.5.0/Huawei_LiteOS/kernel/base/los_misc.c:77-90`：`LOS_Msleep()` 丢弃 `LOS_TaskDelay()` 返回值。
9. 同一内核的 `kernel/base/los_task.c:1286-1316`：第1300行判断 `OsPreemptable()`；第1308行入定时器；第1311行置 DELAY；第1312行直接 `OsSchedResched()`，不经过 `LOS_Schedule()`。
10. `kernel/init/los_init.c:137-152`：osMain 是启动临时任务控制块，优先级为最低优先级加1，即32。
11. `kernel/base/sched/sched_sq/los_sched.c:47-120`：任务切换路径调用 `OsTaskSwitchCheck(runTask, newTask)`。
12. `kernel/base/los_task.c:386-419` 与 `kernel/base/include/los_stackinfo_pri.h:47`：栈检查会解引用 `oldTask->topOfStack`。启动伪任务没有正常任务的栈初始化，零地址栈检查是符合源码和日志的解释。

更准确的故障描述是“osMain 被当成正常任务参与切换，访问其未初始化的栈信息”，不宜直接写成 `OsTaskSwitchCheck(NULL)`。TCB 本身为 NULL 与 TCB 内的栈地址为0不同；日志中的 a0/a1 也是非零值。精确故障指令仍需与板上镜像匹配的 ELF/反汇编确认。

## 4. v1 / v2 / v3 是否正确

### v1 与 v2

只在 `LOS_Schedule()` 阻止调度，无法覆盖上述直接调用 `OsSchedResched()` 的延时路径，这个判断正确。

只在 `OsSchedResched()` 才返回，对 `LOS_TaskDelay()` 确实过晚：伪任务已经入定时器并被改状态。WorkBuddy 指出的“留下后续调度隐患”有源码依据，但具体下一次一定在哪条指令崩溃，不应脱离对应日志和二进制作保证。

### v3

实际补丁在 `kernel/base/include/los_sched_pri.h:155,173,177`，给两种可抢占判定增加 `&& OS_SCHEDULER_ACTIVE`。

- 对 `LOS_TaskDelay`：在入定时器之前返回错误，确实阻止了已知破坏路径。
- 对 `OsSchedPreempt`：第128行先判断可抢占，之后才把当前任务入就绪队列，因此能保护 osMain。
- 正常首次启动走 `osKernelStart → OsStart → ArchStartToRun`，`kernel/init/los_init.c:265` 设置调度启动标志，不依赖上述被拦截的路径。补丁注释中的 `OsStartToRun()` 命名不准确；本树实际函数是 `OsStart()`。
- 已检查当前15:07 ELF对应的 `.asm`：`OsPreemptable` 确实读取 `g_taskScheduled` 并判断启动位，说明门控已进入当前 ELF。
- `los_sched.c` 的 git diff 为空；当前修改包括内核头文件和之前已有的进度文档，工作区并非完全干净。

### 不能忽略的限制

1. **init 延时会被静默跳过。** `LOS_TaskDelay` 报错，但 `LOS_Msleep` 丢弃错误，`osal_msleep` 仍返回0。三次闪灯原本要求的120/80ms等待将不再实现。它能防崩，但不等于应用初始化逻辑完整正确。
2. **全局门控影响其他启动操作。** `kernel/base/los_sem.c:224` 在检查信号量计数之前判断 `OsPreemptable()`，因此即使信号量可立即取得，init阶段也会被拒绝。实际是否影响启动，还要检查调用方并上板验证。
3. **并非所有 API 都在状态变化之前统一经过这个检查。** `kernel/base/los_mux.c:327-337` 在门控前可取得空闲锁；`OsSchedSuspend()` 也会操作其他任务的就绪状态。不能宣称“所有 init IPC/任务操作都不碰任何状态”。
4. **正常运行时判定结果基本保持原意，不代表机器码或执行时间相同。** 增加的读标志与分支可在反汇编看到；也没有执行功能回归和时序测试。

建议：将 v3 视作有依据的防御性候选补丁。应用层的完整修复方向，是让 `app_run` 回调只创建/配置启动任务，将会 sleep 的反馈自检、外设等待和后续初始化放到 `osKernelStart` 之后执行的真实任务中；安排好“外设就绪后再启动依赖任务”的顺序，并处理任务创建失败。不要简单把120ms延时删掉或把长等待全部改成忙等。本轮只复核，未擅自重构该流程。

## 5. Flash 告警的独立含义

- `include/errcode.h:236`：`0x80001341 = ERRCODE_SFC_FLASH_NOT_SUPPORT`。
- `drivers/chips/ws63/porting/sfc/driver/sfc.c:80-95`：读取的 Flash ID 未匹配支持表，选择 unknown Flash 的通用读写配置并置标志。
- 同文件第138—156行：初始化成功后也可能因 unknown 标志返回这个错误码。
- `bootloader/flashboot_ws63/startup/main.c:90-95`：打印 `Flash Init Fail`，该分支本身并不终止启动。

所以它并不直接等于 Flash 坏了。可能是实际型号未收录，也可能是硬件干扰导致 ID 读取异常。日志里程序继续进入 TCA9555 探测，符合“告警后继续启动”。不能仅凭错误码认定是哪一种；需要记录实际 Flash ID，并与支持表和具体板卡版本核对。不能保证 v3 会消除此告警。

本地《HH-D01可以使用的引脚.md》有过时风险：其中写 SCL=GPIO12，而当前 `project/clearchain_soft_i2c.c:8-9` 实际为 **SCL=GPIO13、SDA=GPIO14**。当前日志 probe ok，不应根据旧笔记盲目换线；GPIO复用枚举也不足以证明所有被列为QSPI的引脚在这块板上都被 Flash 实际占用。
