## 本轮（第 3 次）源码级收窄结论（已读 SPI 驱动源码确认）

## ★ 新故障（第 4 次）— 产品 `b` 固件 Load Access Fault 重启循环
- **现象**：烧产品 `b` 后串口反复 `Load access fault` / `Memory map region access fault` → `APP|Reboot core:2` 重启循环，白屏。
  - `mcause:0x5` + `mtval:0x4` + `mepc:0x24cf7a`，`task:osMain`、`phase:Init`。

- `osal_kthread_set_priority`→`LOS_TaskPriSet`→`LOS_Schedule()`：**只挡中断 `OS_INT_ACTIVE`，不挡任务锁** → 非加锁环境下必然走进 `OsSchedPreempt` → 用 osMain 自身 priority=32 入队 → 越界崩。

## ★ 第 13 次（2026-10-05 15:00）—— 【重要修正】① 门控位置错了：LOS_TaskDelay 不走 LOS_Schedule

### 现象

### 根因（① 的设计缺陷，已修正）
- **`LOS_TaskDelay()`（los_task.c:1286）不经过 `LOS_Schedule()`**，它在 1312 行**直接调 `OsSchedResched()`**。

- 关键：`LOS_TaskDelay()`（los_task.c:1286）在调用 `OsSchedResched()`（1312）**之前**已经做了两件事：
  1. `OsTaskAdd2TimerList(taskCB)` —— 把 osMain（伪任务，优先级 32）挂进内核定时器链表；
  2. `taskCB->taskStatus |= OS_TASK_STATUS_DELAY` —— 标记其为"延时中"。
- 若只在 `OsSchedResched` 处拦截，osMain 已被挂进定时器链表且状态已改；当定时器到期（`OsTaskScan → OsSchedWake`），会把优先级 32 的 osMain **重新入就绪队列 → 越界（mtval:0x4）→ 第二次崩溃**。
- 所以门控必须**早于任何任务状态变更**，即提到 `OsPreemptable()` 这个"调度决策唯一汇聚点"。

### 最终版 ①（v3，仅 1 文件 los_sched_pri.h，+19/−3）
- `OsPreemptable()`（~139）判定从
  `BOOL preemptible = (OsPercpuGet()->taskLockCnt == 0);`
  改为
  `BOOL preemptible = (OsPercpuGet()->taskLockCnt == 0) && OS_SCHEDULER_ACTIVE;`
  并加注释说明 WS63 clearchain init 窗口根因。
- `OsPreemptableInSched()` 两分支（SMP `taskLockCnt==1` / 非 SMP `taskLockCnt==0`）同样 `&& OS_SCHEDULER_ACTIVE`。
- 为什么这里能覆盖全部：`OsPreemptable()` / `OsPreemptableInSched()` 是**所有调度决策的唯一汇聚点**——`LOS_TaskDelay`、`LOS_TaskYield`、任务 join、信号量/互斥/队列/事件等待、任务挂起/删除，其调用点一律是 `if (!OsPreemptable()) return ERR_CODE` 形态，没有任何一处依赖它返回 true 才继续。
- 因此 init 阶段（`OS_SCHEDULER_ACTIVE` 为假）任何 delay/IPC 都会**提前以错误码返回、且完全不触碰任务状态**——消除"挂进定时器链表"那颗延时雷。`osKernelStart()` 之后 `OS_SCHEDULER_ACTIVE` 恒为真 → 运行时行为逐字节不变、时序零影响。
