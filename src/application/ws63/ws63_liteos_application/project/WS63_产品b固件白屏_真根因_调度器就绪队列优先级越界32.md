# WS63 产品 b 固件白屏/重启死循环 —— 真根因：调度器就绪队列优先级越界（32），不是栈溢出

> 日期：2026-10-04
> 现象：产品固件 `build_dual.py b` 烧录后仍**白屏 + 反复重启**，串口报 `Load access fault`
> 结论：**与任务栈无关**。真因是 `osal_kthread_set_priority()` 在 app 初始化阶段触发调度器
> 把当前任务重新入队时，用了**越界优先级 32**（合法仅 0~31），导致读数组外内存并解引用 NULL。

---

## 1. 症状（串口关键行）

```
Load access fault
Memory map region access fault
APP|exception:5
task:osMain            <-- 出错任务
phase:Init
mcause:0x5             <-- Load access fault
mtval:0x4              <-- 出错时被访问的地址 = 0x4  ← 关键线索
mepc:0x24cf7a          <-- 出错指令地址
ra:0xa0d68e            <-- 调用者返回地址  ← 关键线索
...
CCDisplayClient  ...  StackSize 0x5000   <-- 20KB 栈修复确实已生效
```

**关键点：把栈从 6KB 改成 20KB 后，`mepc` 依然是 `0x24cf7a`（一字不差）。**
→ 崩溃与栈大小无关，是**确定性代码路径**。

---

## 2. 为什么之前会卡住（误判过程）

| 轮次 | 判断 | 是否正确 |
|------|------|---------|
| 第 1 轮 | LCD 初始化失败 → 白屏 | 部分对 |
| 第 2 轮 | bench 8KB 栈溢出 → 16KB 修复后 bench 通过 | 对（但只针对 bench） |
| 第 3 轮 | 产品 `b` 的 6KB 栈溢出击穿调度器 | **误判**：栈改了，崩溃地址没变 |
| 第 4 轮 | 烧的是旧包 | 对（但改 20KB 后仍崩） |
| 第 5 轮 | 误判为"构建孤儿进程阻塞" | 误判（那俩是另一个项目的 python） |
| **本轮** | **真因：调度器就绪队列优先级越界 32** | **已用反汇编+寄存器现场证实** |

**踩坑根源**：只看"任务表里 CCDisplayClient StackSize 变大 + 仍崩"，就以为还要继续调栈；
实际应该**直接把 `mepc`/`ra` 翻译成函数**，一翻就发现崩在内核调度器里，跟 LCD、跟栈都无关。


### 3.4 反汇编出错那段，看是哪条指令、哪个寄存器
```bash
OD="D:/ws/fbb/src/tools/bin/compiler/riscv/cc_riscv32_musl_105/cc_riscv32_musl_fp_win/bin/riscv32-linux-musl-objdump.exe"
"$OD" -d -C --start-address=0x24cf3a --stop-address=0x24cf88 "$ELF"
```
关键 8 条：
```
24cf5e: addi a1,a1,-812      # a1 = g_priQueueList (0xa12cd4)
24cf62: add a1,a1,a5         # a1 = g_priQueueList + priority*8
24cf64: bnez a2,24cf78       # mode != 0 -> 尾插分支
24cf78: lw  a5,0(a1)         # a5 = g_priQueueList[priority].pstPrev
24cf7a: lw  a4,4(a5)         # ← 崩溃！a5 == NULL，读 NULL+4 = 0x4
```
`mtval=0x4` 与"读 NULL+4"完全吻合（32 位 RISC-V：`LOS_DL_LIST{pstPrev@0, pstNext@4}`）。

### 3.5 用寄存器现场反推优先级实参
异常 dump 里 `a1:0xa12dd4`，而 `g_priQueueList=0xa12cd4`：
```
0xa12dd4 - 0xa12cd4 = 0x100 = 256 = 32 * 8   → 优先级实参 = 32
```
**32 越界！**（合法 0~31，见 `los_task.h: LOS_TASK_PRIORITY_LOWEST 31`）

> 交叉验证可信：dump 里 `a4:0xa54ff0` 正好是反汇编里的 `g_priQueueBitmap`，
> 说明这份寄存器快照确实是故障现场，不是脏数据。

### 3.6 用 `ra` 找真正的调用者（比栈回溯可靠）
`ra = 0xa0d68e`。反汇编 `OsSchedPreempt`：
```
00a0d64e <OsSchedPreempt>:
  a0d658: jal OsPreemptable
  a0d668: lw  a0,1592(a5)     # a0 = g_newTask
  a0d672: lhu a1,6(a0)        # a1 = g_newTask->priority   ← 优先级实参来源
  a0d676: addi a0,a0,56       # &g_newTask->pendList
  a0d68a: jal OsPriQueueEnqueue   # ← 真正调用点
  a0d68e: jal OsSchedResched      # ← ra 正好是这里
```
`ra=0xa0d68e` 说明**调用者不是 `LOS_TaskPriSet`，而是调度器的 `OsSchedPreempt`**。
之前栈里那个 `0x24eaa6`（LOS_TaskPriSet）只是残留干扰帧。

### 3.7 对照源码，确认语义
`kernel/.../sched/sched_sq/los_sched.c:123`
```c
VOID OsSchedPreempt(VOID) {
    ...
    runTask = OsCurrTaskGet();          /* = arch/riscv g_newTask = 当前任务 */
    runTask->taskStatus |= OS_TASK_STATUS_READY;
    OsPriQueueEnqueue(&runTask->pendList, runTask->priority, PRI_QUEUE_HEAD); /* ← 崩 */
    OsSchedResched();
}
```
**即：把"当前任务自己"按它的 `priority` 字段重新塞回就绪队列，而该字段读出来是 32 → 越界。**

## 4. 因果链（完整）

```
clearchain_display_client_entry()                      (app 初始化阶段, 跑在 osMain 上)
  └─ osal_kthread_set_priority(task, 28)               (osal_task.c:56)
       └─ LOS_TaskPriSet(taskId, 28)                    (los_task.c:1342, 校验通过)
            └─ LOS_Schedule()                           (末尾! 无调度器锁 → 立刻切)
                 └─ OsSchedPreempt()                    (los_sched.c:123)
                      └─ OsPriQueueEnqueue(&cur->pendList, cur->priority=32, TAIL)
                           └─ g_priQueueList[32] 越界 → pstPrev = NULL
                                └─ lw a4,4(a5) 读地址 0x4 → Load access fault
                                     └─ 硬异常 → 重启 → 死循环 → 屏幕一直白
```

**为什么 bench 不崩？**
`clearchain_lcd_selftest.c` 的 `lcd_test_entry()` **故意不调用任何 set_priority**，
注释原文：*"explicit priority changes during app initialization previously faulted in
LOS_TaskPriSet on this board"* → bench 保持默认优先级 → 不触发 `LOS_Schedule()` → 不崩。

**产品 b 里"活着的" set_priority 只有一处**（构建日志只编了 5 个 clearchain 文件）：
- ✅ 编入：`clearchain_display_client_entry.c:17` ← 唯一雷点
- ❌ 未编入：`clearchain_device_app.c` / `clearchain_display_link.c` / `clearchain_key.c` / `tcp_client_demo.c`
- ⚠️ `main.c:320` 也有，但它在 `osal_kthread_lock()` 保护下且早已执行完，安全

## 5. 修复

文件：`project/clearchain_display_client_entry.c`

```diff
     osal_task *task = osal_kthread_create((osal_kthread_handler)clearchain_display_client_run,
                                           NULL, "CCDisplayClient", 0x5000);   /* 20KB 栈保留 */
     if (task == NULL) { osal_printk("[CLEAR SLE] client task creation failed\r\n"); return; }
-    (void)osal_kthread_set_priority(task, 28);
+    /* 不在此处改优先级：会触发调度器越界入队而 HardFault。
+       任务创建时已是默认优先级 LOSCFG_BASE_CORE_TSK_DEFAULT_PRIO(=10)，
+       对 50ms 的渲染循环足够。 */
+    osal_printk("[CLEAR SLE] client task created (prio=default), entry done\r\n");
     osal_kfree(task);
```
**做法与已验证可用的 bench 完全一致：初始化阶段不碰任务优先级。**

## 7. 涉及的知识点

1. **RISC-V 异常现场解读**：`mcause=0x5`=Load access fault；`mtval`=出错访问的**地址**；
   `mepc`=出错**指令**地址；`ra`=当前函数的**返回地址**（用它找调用者，比栈扫描准）。
2. **`mtval=0x4` 的含义**：32 位平台 `LOS_DL_LIST{void* prev@0; void* next@4;}`，
   读 NULL+4 就是这个值。**"小地址"= 空指针 + 结构体字段偏移**，是判断空指针解引用的捷径。
3. **ELF 符号定位三件套**：
   - `addr2line -f -C -e elf 0xaddr` → 函数名/文件行（无行信息时只有函数名）
   - `nm -n -C elf` → 按地址排序的符号表，用它**精确框定函数区间**，排除"最近前驱符号"误判
   - `objdump -d --start-address/--stop-address` → 看具体出错指令与寄存器传参
4. **"最近前驱符号"陷阱**：`addr2line` 在没有行信息时给的是"包含该地址的函数"，
   必须用 `nm` 的符号+大小二次确认，否则会误判到邻近函数。
5. **LiteOS 就绪队列结构**：按优先级分桶 `g_priQueueList[OS_PRIORITY_QUEUE_NUM]`（本例 32 桶），
   外加位图 `g_priQueueBitmap`（bit = `PRIQUEUE_PRIOR0_BIT >> priority`）快速找最高优先级。
   优先级**合法范围 0~31**（`LOS_TASK_PRIORITY_LOWEST=31`，数值越小优先级越高）。
6. **`LOS_TaskPriSet` 有前置校验**（`if (taskPrio > 31) return 错误`）——
   所以"实参是 32 却崩在 `OsPriQueueEnqueue`"这个矛盾，直接反证**调用者不是它**，
   进而靠 `ra` 找到真正的调用者 `OsSchedPreempt`。**用矛盾点缩小范围是很有效的推理手法。**
7. **编译期内联**：`OsSchedPrioModify` 被内联进 `LOS_TaskPriSet`，所以栈上会出现
   看似矛盾的地址；不能只看栈扫描，要看 `ra`。
8. **OSAL 任务默认优先级**：`osal_kthread_create()` 固定用 `LOSCFG_BASE_CORE_TSK_DEFAULT_PRIO`
   （本例生成的 `menuconfig.h` 里 = **10**），`osal_kthread_set_priority()` 只是补设。
9. **构建产物 vs 源码**：改源码不重新构建 = 烧的还是旧包。**判断依据是产物时间戳**，
   不是"我记得改过"。
10. **日志反复出现 `Flash Init Fail! ret=0x80001341`**：非致命（有回退），与本问题无关，
   别被它带偏。

---

## 8. 一句话总结

> 白屏重启的真因不是栈溢出，而是 **app 初始化阶段调用了 `osal_kthread_set_priority()`，
> 触发 `LOS_TaskPriSet → LOS_Schedule → OsSchedPreempt` 把当前任务按越界优先级 32
> 重新入队，读越界内存里的 NULL 指针字段（地址 0x4）而 HardFault**。
> 修复：**初始化阶段不要改任务优先级**（与已验证的 LCD bench 做法一致）。
