## 现在是什么问题

当前链路停在“建立 SLE 连接后配对被拒”。`include/middleware/services/bts/sle/sle_errcode.h:99` 将 `0x8000600f` 定义为 `ERRCODE_SLE_PAIRING_REJECT`。`Connected` 仅代表连接已建立，后续配对、MTU 交换、服务/属性发现和数据接收分别需要成功。

板1多次连接回调为 `state=1 pair_state=1`（未配对），随后大多是 `state=2 reason=0x10`。SDK 公开头文件将 `0x10` 定义为远端断链，即板1看到客户端一侧断开；这一观察不能单独证明哪端的配对策略先拒绝。其他日志中的 `0x1c`、`0x7` 在本次核对的公开枚举里没有说明，不擅自命名。

板1的 `peer pairing cleanup request status=0x0` 和 `peer pairing record removal status=0x0` 证明其删除操作完成；之后仍反复断连，说明单独清理板1不是充分解决办法。删除返回成功也不等于证明原本确实存在过期记录。当前日志缺少客户端本地配对状态、配对请求返回码、认证结果，尚不能确定拒绝的底层原因。

## 实际解决了哪些软件问题

读取 SDK `sle_uart_client.c:144` 的停止扫描回调：示例在连接前删除指定目标的本地配对记录。读取 `sle_speed_client.c:206`：示例在配对失败后清理指定对端。读取 `sle_connection_manager.h:724/743`：删除结果由异步 `pair_remove_cb` 报告，不能把请求返回成功当成已经删完。

原板2代码直接连接；配对失败只打印错误；断开后立即重扫，因此客户端残留记录没有恢复路径，且快速重复相同失败。本次仅修改 `clearchain_display_client.c`：

1. 首次扫描找到 `clear_main` 并停止扫描后，查询本地配对状态，记录查询结果；仅删除这个目标设备的本地记录，每次启动最多一次。
2. 删除请求被接受后，等待匹配目标地址的完成回调，再连接。请求失败则保留诊断日志并尝试正常连接；完成状态失败同样明确记录，不假装清理成功。
3. 若 5 秒内没有完成回调，打印超时并停止该次连接尝试，提示复位；不在删除尚未结束时并行连接。
4. 连接与配对回调增加状态、断链原因、请求返回码；注册认证完成回调，只打印状态，不打印密钥。
5. 仅 `SLE_PAIR_PAIRED` 直接交换 MTU；`SLE_PAIR_PAIRING` 等待配对完成，避免把“正在配对”误作“已配对”。成功完成回调还检查当前连接及目标地址。
6. 断开后的扫描重试间隔 2 秒，在客户端任务循环里执行，不在协议回调里睡眠。间隔用于减少失败刷屏和过快重连，不保证配对成功。
7. 保留上一版先查询主服务 `0x2222`、再在其句柄范围查询属性 `0x2323` 的修正。

关键代码：目标连接/清理约 142–196 行；连接及配对约 208–280 行；回调注册与任务内超时/延后重扫约 422–467 行。板1源文件本次没有修改。
