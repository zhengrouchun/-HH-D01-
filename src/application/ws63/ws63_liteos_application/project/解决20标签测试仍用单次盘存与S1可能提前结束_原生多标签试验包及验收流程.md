# 解决20标签测试仍用单次盘存与S1可能提前结束

日期：2026-10-06。本文面向广东现场板1/板2硬件联调。真实后端由天津队友笔记本提供；离线试验结果不能当作后端风险判定。

## 问题、原因和本次处理

此前离线板1虽然每约300 ms重复发送一次 `0x22` 单次盘存，读到首张后没有立刻停止，却**不是** R200 原生 `0x27` multi-poll。`clearchain_device_session.c` 原来还允许 S1 在 `unique >= tags_expected` 时早于10秒结束；离线 `tags_expected=-1` 不触发，但真实API批次可能触发。20标签测试需要先区分协议模式和完整10秒窗口。

本次只对板1离线bench启用原生多标签连续盘存：每个窗口开始发送一次 `0x27`（rounds=65535），结束、切阶段或异常时发 `0x28` 停读；解析保留EPC/RSSI与去重，窗口汇总增加 `stop_tx`、`ack`。UART环形缓冲从1024增到4096字节以承受多标签通知突发。S1不再因预期数量提前结束，固定10秒；S2～S5/CP固定3秒。扫描中按阶段键时增加 `STOP_SCAN before SELECT_MODE` 和 `SELECT_MODE request` 串口标记。真实API版仍使用原先的每300 ms单次盘存，须等本试验包在实板证明 `0x27`可用后再决定是否给上传版启用；本次未动板2。

本地10秒计时也会被后端主动下发的DONE、Stop、断网等状态中断；真实API联调时若提前DONE，应核对队友服务端的结束规则，不能把本地计时修正误当作服务端已承诺完整10秒。

SDK的 `build_dual.py api_bench` 构建、签名、manifest和 `publish_role.py api_bench` 发布校验通过。板1试验包：`D:/ws/fbb/src/output/clearchain/_flash_ready/ws63-liteos-app_all_BOARDA_OFFLINE_R200_MULTI_20261006_e91a842e.fwpkg`；SHA256 `e91a842e2d0462b1089e75ebbc2386d5794bef05a14031984e1f5629898e6744`，1539432字节，metadata 为 `r200_native_multi=true`、`offline_bench=true`、`http_enabled=false`、`hardware_verified=false`。目标配置构建前后SHA256仍为 `a2721343796f200331ce8e2eca7e62667cd9862569c082b494f1426d709f8780`。原已实板读到三张的 `...BOARDA_OFFLINE_REAL_RFID_20261006_b6c085f3.fwpkg` 保留作对照。**新multi-poll包尚未实板验证。**

## 晚上20张测试的顺序与记录

1. BurnTool只刷板1新试验包，确认100%和成功；板2保持配套v4。复位两板，确认SLE connected、服务/属性发现、ready。串口分别保存带时间戳的板1/板2完整日志。新板1启动应有 `OFFLINE BENCH: native R200 multi-poll`。
2. 先用此前已读成功的一张标签：移走其他标签，固定距天线约10～20 cm、方向不变，按S1一次。看到 `capture begins mode=S1` 和 `[R200 MULTI] ... started`，等足10秒，不按其他键。应有该EPC、`unique=1`、停止标记、`[R200 BENCH MULTI] tx=1 stop_tx=1`，板2最终`tags=1`。若模块对0x27没有回复、出现`stop failed`或持续丢帧，先停止20张测试，把这些日志交回分析；原单次盘存包可作回退对照。
3. 用三张已知标签重复一轮S1。单张和三张均正常后，再把20张逐张核对EPC清单，平铺或扇形分开，不重叠，移走读区外的其他UHF标签。使各标签尽可能处在天线有效区，起始距离约10～20 cm；保持天线、标签朝向与R200供电不动。当前固件**没有设置R200射频功率的命令**，不能声称软件已调高功率；若通过模块已有的配置方法调整，记录调整前后实际功率值且每组只改这一项。
4. 按S1一次，完整等10秒；窗口结束后才按下一次S1。相同摆放做三轮，每轮记录：开始/结束时间、窗口10秒、已放20张、`final accepted unique=N samples=M`、各EPC的RSSI范围、`tx/stop_tx/rx/epc/rejected/dropped/bad_frames/uart_errors`、板2最终Tags read=N。目标是20/20；不足20时列出未读EPC，不能只写“约20张”。单EPC多次RSSI用最小/最大值及跨度、三轮是否反复漏读来判断稳定性，不凭某一个RSSI值下结论。若`rx=0`或`dropped>0`，单独记录，不归因于标签重叠。
5. S5：只放一张已知标签，按板1 S5一次并等约3秒；确认板1`mode=S5`、EPC、`final accepted unique=1`和板2`stage=5 tags=1`。S5结束后按第二颗的D3，预期`Extra key 8 pressed: mode=5 availability=0`；这是可用性规则和实体键输入检查，不是打开图像页面。
6. 离线切阶段：只放一张标签，按S1，待板1有EPC且状态`phase=2`，在10秒结束前按S2一次。应依次看到`STOP_SCAN before SELECT_MODE S2`、旧模式`armed=0`、`SELECT_MODE request S2`、新模式S2开始；被中断的S1不应有`final accepted`，新S2是独立3秒窗口。此步仅验证离线状态机；真实HTTP命令先后顺序仍需后端API接通后由板1和后端日志共同确认。

## CP与新增键按之前文件的验收边界

- CP没有已定义的独立实体键。当前离线包只能由S1～S5触发扫描，无法把S5或D4私自改成CP。拿到真实API v2地址后，用手机控制面板或 `tools/device_control.py --url http://可达地址:端口 --command SELECT_MODE --mode CP` 选CP，再用一张标签观察板1、板2及后端，CP窗口为3秒且无批次时不应伪造batch_id。此时按D2，预期`mode=6 availability=0`；D2是否发送OPEN_VIEW由产品/后端另行确定。
- 第二颗TCA9555的方向键与D1～D4已在上一轮日志中各按两次并记录`Extra key 1..9 pressed`，物理输入不必重做。可补S4/S5下D3的软件可用性。旧嵌入式规格列方向键v1不使用，D键OPEN_VIEW为可选且由手机显示完整页面；概念变更文件规定WS63 LCD只显示简要状态，不要求在板2实现历史/原始阵列/图像页面。若团队后来修改这项范围，应先更新共同规格与接口，再实施功能。

## 当前至少接线及你负责的完成条件

- 板1：R200稳定5V和天线、R200与板1共地，板1GPIO15/TX→R200 TTL_RX，GPIO16/RX←R200 TTL_TX（3.3V TTL）；第一颗TCA9555用板1 3.3V/GND、GPIO13/SCL、GPIO14/SDA，A0/A1/A2接GND为0x20，P10～P14接S1～S5（各有10k上拉至3.3V，按下接GND）。这套是当前固件启动和阶段扫描的最低实物条件。
- 板2：LCD稳定3.3V与共地；SCK=GPIO7、MOSI=GPIO9、CS=GPIO8、DC=GPIO1、RESET=GPIO14、背光BL=3.3V高电平。板1和板2之间使用SLE，无须跨板接UART、SPI或I²C。第二颗TCA9555若保留九键：同一板1 I²C与3.3V/GND，A0=3.3V、A1/A2=GND为0x21，P00～P04=上/下/左/右/OK，P10～P13=D1～D4；它不是核心RFID/SLE链路的先决条件，现已在实物日志测通。
