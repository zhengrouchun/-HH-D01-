## 已确定的故障链

板2旧诊断版请求 `SSAP_FIND_TYPE_PROPERTY`（type=3），SDK 返回 `property uuid_len=2 ...2323`、handle=17、操作位 `0xd`，本地检查 `match=1 notify=1`，完成 status=0。但同一次发现没有调用服务回调，`service_match=0`；旧完成条件要求服务和属性同时为真，因而打印 `display property not found` 并且没有发就绪写命令。这里是客户端发现流程和判定条件失配，不是该日志所能支持的“属性不存在”。

板1旧运行日志持续 `Can not find AP, try again !`，没有 `STA try connect.` 或 `[DEVICE] Wi-Fi ready`；完整附件中重复 33 次，扫描数量为 14 至 32 个 AP。`include/my_wifi_api.c` 的 `example_get_match_network()` 使用 SSID 长度与字节严格匹配；目标没选中就不会进入认证。因此当前先处理固件内 SSID、热点频段和热点实际可见性，不能把这一阶段归因为密码错误。

实际包内字节核对：`output/clearchain/board_a_api/ws63-liteos-app-sign.bin` 和旧 `_flash_ready/...ROLEAPI-20261005-0859.fwpkg` 均包含 `@Ruijie-456`，不包含 `stu.gpnu.edu.cn`。当前工作区 `clearchain_config.h` 已由用户改为 `stu.gpnu.edu.cn`，但它还没有进入板上旧包。此事实可解释“源码看起来改了，板子仍扫描旧热点”的现象。新 SSID 是否属于可用的 2.4 GHz 普通密码热点，还需现场确认；若它要求校园网页认证或企业 EAP，当前 `wifi_connectTo_AP()` 的预共享密钥配置流程可能不适用。

## 已完成的板2修正与产物

`clearchain_display_client.c`：

1. MTU 成功后先请求 `SSAP_FIND_TYPE_PRIMARY_SERVICE`（type=1），通过服务回调检查 UUID `0x2222`，保存服务的起止 handle。
2. 第一阶段完成后，请求该 handle 范围的 `SSAP_FIND_TYPE_PROPERTY`（type=3）；属性回调检查 UUID `0x2323`、NOTIFY 位及 handle 是否落在所选服务内。
3. 第二阶段完成后才设置 ready，并向属性写入 `R` 加协议版本字节；断连时清理阶段、handle 和服务状态。保留诊断输出，遇到错误明确区分服务不存在、属性不存在或过期回调。

SDK `include/middleware/services/bts/sle/sle_ssap_stru.h` 定义 type=1 为主服务、type=3 为属性；`sle_ssap_client.h` 记录了两种结果及发现参数。`application/samples/bt/sle/sle_speed_client/src/sle_speed_client.c` 使用 type=1 并处理服务回调，证明此接口路径在本 SDK 中有示例；本项目服务 UUID 及属性定义来自 `clearchain_display_link.c`。

## 硬件当前进度

- 板1在接线后 `TCA9555 0x20 probe ok`、R200 UART ring buffer 就绪、五个阶段键输入初值为高、SLE 广播并被板2连接；说明这些初始化路径已走通，但还需按键按下、RFID 实读和长时间供电稳定性测试。
- `TCA9555 0x21` 报 `0x80001314`，`include/errcode.h` 定义为 I2C ACK 失败。当前 `clearchain_key.c` 把 0x21 用于额外按键；若仅安装一块 0x20 扩展器，这与 0x20 主芯片成功可并存。是否需要额外九键，取决于实际接线清单。
- 板2 LCD 报告 SPI0 480x320 初始化，SLE 接收属性已证明链路能交互；LCD 实际显示效果仍需现场目视，初始化日志本身不能替代画面验收。
- 两板日志都有 `Flash Init Fail! 0x80001341`，在 `include/errcode.h` 是 `ERRCODE_SFC_FLASH_NOT_SUPPORT`；SFC 代码有未知 Flash 回退路径，且两板随后运行应用。这需要记录并在将来核对 Flash 型号，但不是当前属性失配的解释，也不支持直接擦除全片。
- 板1日志有一次 SLE 断开后数秒重连。单次日志未包含断连原因，暂不能确定是供电、信号或用户复位造成。属性流程修好后再观察是否持续掉线。
