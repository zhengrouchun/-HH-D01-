# 解决20张标签摆放和串口统计不清：配套烧录包与S5、CP、切阶段操作说明

日期：2026-10-11。用户负责广东现场硬件；队友笔记本运行真实后端。本文记录离线试验包能验证的部分、必须等API地址的部分和完整操作。上次关于多标签命令与S1窗口的原因、最初构建方法见《解决20标签测试仍用单次盘存与S1可能提前结束_原生多标签试验包及验收流程.md》。

## 问题与原因

“逐张确认”和“20张一起测”是两件事。逐张确认只为建立贴纸编号与EPC的对应表；正式多标签盘存必须让20张**同时**在天线读区，位置、朝向和功率在一轮及三轮之间保持不变。若在10秒内手持一张张轮流靠近天线，测到的是人工依次出示的速度，不能证明20张同时盘存能力。10～20厘米是**每张标签到天线的起始读距**，不是标签之间必须相隔20厘米；标签彼此不要叠压、贴在一起或被金属遮挡。

另一个误区是把离线模拟状态当真实后端命令。离线板1可以测原生R200多标签盘存、S5、第二颗TCA按键及本地Stop→Select顺序；它关闭HTTP，没有真实CP模式入口，也不会访问队友API。CP无确定实体键；按旧嵌入式规格从手机或电脑选CP，后端可达后才能验真实CP和HTTP命令顺序。任何离线LOCAL TEST画面都不代表批准、风险或批次业务结论。

## 包与烧录

本次板1文件名：`ws63-liteos-app_all_BOARDA_OFFLINE_R200_MULTI_20261011_4c79bad5.fwpkg`，SHA256为`4c79bad5a22c0a92aaa90d33d165e1e095a2e10c9e341318d55b29a313dab440`。配套板2文件名：`ws63-liteos-app_all_BOARDB_V2_LCD_SLE_20261006_d0899e0d.fwpkg`，SHA256为`d0899e0de50d1e702cbba1fe4466e5ff1feec9981c4b72f8495798463b9df49d`。新板1包构建、签名、角色、manifest和文件哈希检查通过，`hardware_verified=false`表示还没有用户这块R200的原生multi实测。

交付目录里有板1离线multi-poll固件、配套板2 v4固件、各自的metadata与SHA256。BurnTool只选择`.fwpkg`，不可直接选压缩包或`.json`。如果板2已是配套v4、SLE正常，只烧板1即可；若板2不是v4，分别给两板烧正确文件。每块等待100%与成功提示后复位，打开两个串口，确认板1`OFFLINE BENCH: native R200 multi-poll`、板2连接、服务发现和ready。新原生multi-poll固件仍需实板确认；遇到`start failed`、`stop failed`、无EPC或大量掉帧，立即保存串口，不继续20张，旧单次盘存包留作回退对照。

## 标签摆法与完整操作

1. 给20张标签贴1～20号，其他标签移出读区。逐张把一张标签放在天线前约10～20厘米、同一朝向，短暂读取并把编号与EPC记录下来；这一步可以单独进行，**不计入正式20张窗口**。核对没有重复EPC。确认R200使用其配套天线和稳定电源。
2. 在桌面或非金属支架上将20张平铺成几排或扇形，标签正面朝向天线，不重叠、不紧贴；天线固定，使全部标签尽量落在10～20厘米起始读距及有效读区。空间不足时记录实际远近位置，不把“距离20厘米”理解为标签间隔。先用当前功率测一组；如使用R200已有的配置方式增加射频功率，记下**实际设置值**再测第二组。当前固件没有自动调功率命令，不要声称烧包后功率已提高。
3. 新包先用1张做S1完整10秒，确认`[R200 MULTI] ... started`、该EPC、`... stopped`、`final accepted unique=1`与`[R200 BENCH MULTI] tx=1 stop_tx=1`，板2最终`tags=1`。再用3张做一轮，确认最终`unique=3`。任一前置不通过时先查日志，不直接做20张。
4. 正式20张同时摆好后，按板1 **S1一次**，松开，不再拿动任何标签，完整等10秒直到`final accepted`和`[R200 BENCH MULTI]`。窗口结束后才开始下一轮；相同摆位做三轮，不在三轮间挪天线/标签。20/20是目标，实测低于20也如实记录。
5. 每轮从板1串口保存：开始/结束时间、每条`EPC=... RSSI=... unique=... samples=...`、最终`unique`与`samples`、`tx/stop_tx/rx/ack/epc/no_tag/rejected/dropped/bad_frames/uart_errors`。板2串口保存本轮最终`[CLEAR DISPLAY] ... stage=1 phase=3 ... tags=N`。用预先的20张EPC表减去本轮出现过的EPC，就是漏读清单。对**同一EPC**取本轮所有RSSI的最小和最大，再比较三轮的范围及漏读是否重复；移动标签后出现的变化不能归为固定摆放下的不稳定。板2`samples=0`是当前传输字段固定值，以板1`samples`为准。串口工具保存**原始完整日志并带时间戳**即可；无需接第二根R200串口。把三轮板1和板2日志发回后，可直接计算漏读与RSSI范围。

## S5、扫描中按S键与CP

6. S5：移开其他标签，只放一张已知标签；按板1 S5一次并松开，完整等3秒。板1应有`capture begins mode=S5`、EPC、`final accepted unique=1`，板2最终`stage=5 phase=3 tags=1`。窗口结束后按D3，板1应有`Extra key 8 pressed: mode=5 availability=0`。这只验证D3输入与模式允许标记，不会打开图像页。
7. 离线切阶段：仅放一张已知标签，按S1启动；等板1已记录EPC且`state ... mode=S1 phase=2`，在10秒结束前按S2一次。观察`[R200 MULTI] ... stopped`，再看`STOP_SCAN before SELECT_MODE S2`、旧状态`armed=0`、`SELECT_MODE request S2`、新S2窗口开始。旧S1不应有`final accepted`；S2在3秒后结束。离线包里的STOP_SCAN是本地状态机模拟，串口文字不能证明真实HTTP请求已经到队友电脑。只有后端接通后，才能在板1和队友后端日志共同核对真实STOP_SCAN先于SELECT_MODE。
8. CP：**当前离线包不能完成真实CP。** 有从广东可达的API v2完整地址后，运行现有`tools/configure_backend_and_build_board1.cmd`输入该地址及广东现场Wi-Fi，预检查通过后只烧新API板1包，板2v4保留。由手机选CP，或在仓库根目录运行`& 'D:/ws/tools/python/python.exe' application/ws63/ws63_liteos_application/project/tools/device_control.py --url 'http://实际可达地址:端口' --command SELECT_MODE --mode CP`；等板1收到CP、armed和扫描开始，再扫描一张标签并核对板1、板2及后端记录。CP无批次时不伪造batch_id，窗口按3秒；若后端规定必须显式START_SCAN，再运行同一工具并将命令改为`--command START_SCAN`。此时按D2，可检查`mode=6 availability=0`；D键打开手机视图是可选业务功能，按旧规格由手机展示完整历史/原始阵列/图像。没有后端地址时不能提前给出可工作的API烧录包。

## 这次代码逐句作用与文件位置

- `r200_protocol.h`新增有名称的协议常量：回复帧类型用于区分命令答复；multi与stop命令号用于区分连续盘存和停读；最小轮数、multi数据长度和盘存参数用于组帧及校验和。`r200_protocol.c`逐句作用：先组装固定的命令帧；检查输出指针、空间和轮数；把轮数拆成高低字节；按协议计算校验和；复制到调用者缓冲并返回长度。停读函数组装并复制stop帧。解析函数用命名命令号识别multi通知。这些常量表达协议字段含义，避免在业务代码里直接比较不明用途的十六进制数字或使用`0U`表示不合法轮数。
- `clearchain_device_app.c`的`bench_start_inventory()`：分配能容纳R200帧的缓冲；生成最大轮数的原生multi命令；经UART发出；失败时打印原因并返回错误；成功时标记盘存已启动、增加发送次数并打印开始日志。`bench_stop_inventory()`：若未启动则直接返回；若已启动，先清启动标记，再生成并发送stop命令；失败打印警告，成功增加停读次数并打印结束日志。两个函数只在离线bench固件启用。
- 同文件`reader_tick()`：在窗口有效时读取R200串口帧；命令确认帧单独计为`ack`；标签通知解析出EPC/RSSI；每个EPC第一次出现才增加unique，每次有效通知都增加samples；串口逐条打印EPC/RSSI供后处理。同文件`consume_keys()`：取阶段键事件；取消旧采集并清串口；读取当前状态；若为SCANNING先请求STOP_SCAN并接收状态；再请求SELECT_MODE并接收新状态。失败时不把选择记为成功。离线分支模拟这些状态，HTTP分支才对真实API发请求。
- `clearchain_device_session.c`用`CC_S1_WINDOW_MS`表示S1十秒，用`CC_OTHER_WINDOW_MS`表示其他模式三秒，用`CC_EMPTY_COUNT`表示尚无样本；`cc_session_finished()`只在当前窗口确已运行到对应时长时返回完成，避免到达预期标签数后提前结束本地S1窗口。`r200_uart.h`将RX环形缓冲增至4096字节，以容纳multi-poll突发通知。`publish_role.py`检查包角色、manifest、二进制标记与SHA256，并在metadata标注`r200_native_multi`、`http_enabled`和`hardware_verified`；这些字段对应包的实际功能与验收状态。

为避免不明用途的裸数字，`clearchain_device_app.c`还把设备循环里每个时长分别命名：`CC_NO_WAIT_MS`表示读UART只查看现有帧、不等待；`CC_MAX_FRAMES_PER_TICK`限制单轮最多处理的帧数，让按键与SLE有运行机会；`CC_ONLINE_STATE_POLL_MS`与`CC_OFFLINE_STATE_POLL_MS`分别表示正常和离线状态查询间隔；`CC_SINGLE_INVENTORY_INTERVAL_MS`只用于尚未启用原生multi的API固件；`CC_PENDING_POST_INTERVAL_MS`表示上传缓存读数的间隔。`r200_protocol.h`的三个协议常量分别说明回复帧类型、连续盘存命令号和停读命令号。新增及修改的这些语句都使用名称表达作用，不再在这些路径写难辨用途的`0U`等字面量。

逐句看原生multi窗口：①`uint8_t bytes[R200_MAX_FRAME_SIZE]`保留一块足够放完整R200命令帧的内存；②`size_t length`保存本次编码后的实际命令长度；③`r200_protocol_build_multi_inventory(...,UINT16_MAX)`编码持续足够多轮的盘存命令；④`r200_uart_write(bytes,length)`把它送到R200；⑤任一环节失败则打印`start failed`并取消本轮；⑥成功后`g_multi_inventory_started=true`记住需要在窗口终止时发停读；⑦`g_reader_diag.tx++`记一次启动命令；⑧开始日志让串口直接证明新命令已发送。停读函数先检查是否真的启动，清标记防止重复停读，再编码/发送stop；成功才增加`stop_tx`，失败明确打印警告。接收循环先读帧，将命令答复计入`ack`，其余帧解析为标签、无标签或拒帧；有效标签调用会话去重与计样，逐条打印EPC和RSSI。`cc_session_finished()`比较当前时间与开始时间的差值，S1达到10秒、其他模式达到3秒才触发本地结束。这些是当前烧录包负责的每个关键语句及对应串口证据。
