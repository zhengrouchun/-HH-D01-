## 本次是什么问题、由什么引起

板2从 `boot.` 到 `[CLEAR SLE DIAG] client two-stage-discovery-20261005-v2` 证实新固件正在运行，LCD 初始化也到达完成日志。随后约 30 次连接均在服务发现前报 `[CLEAR SLE] pairing failed: 0x8000600f`，紧接着断开重扫。板1同时有约 52 次快速连接、断开和重新广播，双方互相印证为同一条 SLE 配对失败循环。

`include/middleware/services/bts/sle/sle_errcode.h` 从 `0x80006000` 起定义通用错误，`0x8000600f` 明确对应 `ERRCODE_SLE_PAIRING_REJECT`（配对被拒）。因此前一次的“查询服务再查属性”修正这次尚未运行到，不能从新日志评价属性发现 v2 是否成功，也不能归因 LCD 或属性 UUID。

反复刷完整双板烧录包后，保存的对端配对记录不一致是合理且可检验的主要假设；当前日志**不能证明**它是唯一根因。SDK 的 `sle_speed_server`、`sle_speed_client` 样例在配对/认证失败时使用 `sle_remove_paired_remote_device(addr)` 清理指定对端的记录，而不必清空所有配对。`sle_connection_manager.h` 明确该操作的结果通过 `pair_remove_cb` 异步返回。

## 本轮修复及安全边界

仅改 `clearchain_display_link.c` 的板1服务端：

1. 连接状态回调增加 `state`、`pair_state`、`reason`，为下一次日志保留协议状态证据；记下连接时间。
2. 如果断连发生在成功交换 MTU 之前、距连接不足 4 秒，且本次启动尚未尝试清理，则仅调用 `sle_remove_paired_remote_device(addr)` 删除当前连接的板2记录。
3. SDK 接受删除请求后，等 `pair_remove_cb` 回报结果再恢复广播，防止板2在记录尚未删完时立即重连；调用失败则直接恢复广播。
4. 只尝试一次，其他对端的配对记录不动。启动日志标识为 `server peer-bond-recovery-20261005-v1`。

这一步针对最可能的旧配对记录失配；若 SDK 返回“无记录”或删除成功后仍被拒，新日志可立即改变判断。没有清空 NV、执行 Erase all、修改 efuse，也没有把配对被拒武断说成射频硬件损坏。板2客户端无需修改，保留原有 `two-stage-discovery-20261005-v2` 固件。

## 现场操作、预期结果与分支

1. 先关闭板2电源；板1断开外设后选择实际 COM，在 BurnTool 选上面板1新包，Connect 后按板上实体 RST，等待整个包成功。再断电恢复板1外设。
2. 用 115200 串口打开两块板的日志。先启动板1，确认 `server peer-bond-recovery-20261005-v1` 和 `server advertising`；再启动板2，确认 `client two-stage-discovery-20261005-v2`。
3. 第一轮连接仍可能短暂断开。板1应出现 `peer pairing cleanup request status=0x0`，随后 `peer pairing record removal status=0x0`；如果返回非零，记录**原值**，不要反复擦除或连续烧录。
4. 后续重新连接若成功，板2应继续打印 `ssapc exchange info`、`discovery request ... type=1`、服务回调、`property request`、属性回调和 `service discovery complete`。板1应停止每秒反复连断；最终确认 LCD 画面或 `[CLEAR DISPLAY]`。
5. 如果清理成功仍报 `0x8000600f`，需完整保存两板从启动到首轮失败的日志，尤其是板1 `pair_state`、`reason` 和清理回调结果。此时继续检查配对参数、身份/地址记录或 SDK 配对行为，不能继续假定只是缓存问题。

## 后端与硬件分别到哪一步

板1这次附件明确有 `Srv:find ssid[stu.gpnu.edu.cn]`、`STA connect success.`、`STA IP 10.231.80.243` 和 `[DEVICE] Wi-Fi ready`，说明 Wi-Fi 扫描、关联和 DHCP 已过。`[DEVICE] backend offline` 发生于启动后约一秒，而 Wi-Fi 任务五秒后才开始连接；更关键的是 `profiles/board_a_api.config` 关闭了 HTTP 两个开关，`clearchain_device_http.c:exchange()` 在 socket 创建前直接返回。因此这个日志**不能**证明服务器离线；后端地址、服务路由及启用通信仍待单独联调。

硬件方面：板1 TCA9555 `0x20` 探测、R200 UART 初始化、五个主按键初始读取和 SLE 广播正常；板2 LCD 初始化及 SLE 扫描/连接正常。`0x21` TCA9555 没应答只涉及额外按键，若现场计划装第二块扩展器才需查其电源、地址脚及 SDA/SCL。当前没有 Load access fault。两板的 `Flash Init Fail 0x80001341` 后均能启动应用，先记录为独立告警，不把它当成本次配对拒绝的直接证据。配对恢复后仍需按键实按、RFID 实读、LCD 实显和持续连接测试。
