## 哪些是真实数据，哪些是模拟数据

- `[R200 TEST] RX bytes=...`：真实UART接收帧，诊断代码从接收队列获取后打印。
- `[R200 TEST] EPC=... RSSI=...`：从上述有效标签通知解析出的实际标签编号及模块报告的RSSI。RSSI会随距离、方向及环境变化，不是距离的直接测量值。
- R200的`unique`和`samples`：根据实际EPC采样计算的窗口统计，不是后端批次统计。
- LCD诊断照片中的`Tags: 3 / 5`、扫描进度60%、风险0%/40%/80%、APPROVED/MONITOR/REJECT、S1/S4/S5标题：`clearchain_lcd_selftest.c`直接赋值的模拟页面数据。
- LCD诊断中的`Server offline`和`Retrying...`：模拟离线页面，不代表本次诊断实际访问了服务器。
- `[LCD TEST] sample=... version=...`：本地模拟页面序号和版本，不是实际后端state_version。
- LCD诊断的SYS INFO内存统计：真实运行时统计。用户正文中多次为used=114276、free=80544，未出现原初始化崩溃或SPI失败日志。

两个诊断应用相互独立。屏幕上的3/5并不是这次R200读数通过SLE传过去的显示；当前组合没有启用应用SLE。此前正常SERVER/CLIENT固件已经实板验证星闪连接、认证、配对、服务发现和状态通知。

## 问题是什么、如何解决

原正常LCD初始化发送0x21开启反相，与当前这块屏的正确显示设置不一致。仅有初始化成功日志不能判断颜色，故先用同一SPI/LVGL路径输出标注名称的五色块，对比OFF/ON，再显示已知颜色的模拟结果页。实物照片与代码阶段对应后，正常初始化改发0x20，并增加启动标记。

原API读卡受业务状态控制，后端离线时不进入实际扫描；靠近标签没有输出不能证明R200损坏。前一轮已新增独立R200诊断入口，调度启动后主动发0x22，接收原始帧并打印EPC/RSSI。本次用户烧录实测证明UART和RFID基本通路有效，本轮无需继续修改R200协议代码。

方法：隔离业务依赖、已知图案对照、原始帧校验、从RX独立提取EPC/RSSI、窗口去重统计、SPI命令主机检查、角色归档与包内启动标记检查、SHA256核对。串口工具会在一行甚至一个十六进制字节中间插入时间戳，复核时拼接后再判断校验，不把显示换行误判为模块坏帧。

## 接下来怎样操作

1. 如需核对7个EPC各属于哪张卡，先保持板1R200诊断包，移开附近其他标签，逐张放入约20秒，再全部移开；核对单张EPC一致和空窗口归零。最后将选定3张一起摆放，保持几分钟检查读数和错误计数。已经完成的基础读卡不必重复从UART排障开始。
2. 恢复双板联测时，板1烧上述正常SERVER/API包，板2烧本轮正常CLIENT/LCD新包。关闭占用COM的串口助手，分别等待BurnTool成功，再释放端口读取日志。保持已验证的R200和LCD接线。正常板1使用已装的0x20 TCA；第二颗0x21未安装，不要求现在补装。
3. 先启动板1，再启动板2。板1应有`server advertising`；板2应有客户端v3标记和LCD校准OFF标记，随后连接、认证/配对、服务发现及状态接收成功。屏幕颜色应与本次正确页面一致，且不再循环`[LCD TEST] sample`模拟页面。
4. 双板连续运行至少5分钟，记录是否自行断连、花屏或崩溃；记录时间后手动复位板2一次，验证重新连接和恢复显示。两板采用星闪无线链路，无需接两板之间的TX/RX。
5. 保持已装0x20及S1～S5接线，每键按一次，检查板1`Stage button N pressed`日志，验证物理输入和消抖。当前后端/HTTP门控未开，可能紧接`SELECT_MODE failed: HTTP -1`，页面不一定随按键改变；此时验收按键日志即可。CP是屏幕显示项，本屏不带触摸，不以点击屏幕作为输入测试。
6. 真实扫描上传阶段再提供可访问的API Base URL及所在网络，按既有API v2合同修正armed、Stop取消、版本变化、空final和CP等差异。用刚读到的真实EPC登记测试批次后，验收Start→采样→上传→后端结果→SLE→LCD，最后验收手机控制、IN/OUT和工厂RSSI基准。

前5项不需要真实后端地址。当前业务固件离线不主动扫描，因此恢复正常包后标签靠近不输出，不推翻这次R200诊断实测。
